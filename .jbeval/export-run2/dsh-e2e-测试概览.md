## 1. 端到端测试（E2E）是什么

端到端测试（End-to-End Testing，简称 E2E）是一种从用户或外部客户端的视角，验证整个软件系统完整工作流的测试方法。它不同于单元测试（只验证单个函数或模块）和集成测试（验证模块间的协作），而是将系统作为一个整体来考察。

> 教学抽象：可以把 E2E 比作一条流水线的最终质检——不是检查单个零件，而是让整个流水线跑起来，确认最终产品符合预期。

在 API 服务的场景下，E2E 测试通常会通过 HTTP 请求真实地访问服务，携带真实的认证信息，依次触发多个接口，最终检查返回结果以及系统状态。

## 3. 整体思路：以 FastAPI 交互式文档作为测试入口

DSH E2E DeepSeek Test 的核心思路是：**不绕过用户入口，而是直接使用 FastAPI 自动生成的交互式文档（Swagger UI）作为测试的前端入口**。

具体做法是：

1. 启动被测服务；
2. 用浏览器自动化工具打开 `/docs` 页面；
3. 在交互式文档中模拟用户操作：选择接口、填写请求参数、点击执行按钮；
4. 检查返回的响应状态码、响应体是否与预期一致；
5. 将关键步骤串联起来，形成完整的业务场景。

这种做法的本质是：把测试目标不仅看作“接口本身”，还包括了“接口文档是否可用、OpenAPI 模式是否正确”。

## 4. 为什么选择 FastAPI 交互式文档

根据 FastAPI 官方教程，FastAPI 会自动生成两种交互式 API 文档：`/docs`（Swagger UI）和 `/redoc`（ReDoc）。[^1] 这些文档基于 OpenAPI 模式自动生成，因此与代码保持同步。[^1]

选择 `/docs` 作为测试入口的主要理由如下：

- **文档与代码同源**：`/docs` 是自动生成的，能够反映当前的路由、请求与响应定义。
- **无需额外编写 API 客户端**：交互式文档本身就提供了发起请求的界面，可以直接填写参数并调用接口。
- **便于人工排查**：当自动化测试失败时，测试人员可以打开同一个 `/docs` 页面手动重现问题。

需要强调的是，选择交互式文档作为入口并不代表它替代所有其他测试方式；它的优势在于额外验证了“文档—实现”的一致性，同时降低了测试脚本维护成本。
